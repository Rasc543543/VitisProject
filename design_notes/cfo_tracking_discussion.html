§1 背景與優化目標

原始 ref_rx_packed 每幀固定執行 Loop_CFO_Scan，對所有 141 個頻率偏移量逐一計算 pilot 子載波能量，佔整幀處理時間的 94%。

Loop_CFO_Scan：141 offsets × 139 pilots × II=1 = 42,864 cycles ≈ 428 µs / frame 總 frame time（原版）：~1001 µs → Data Rate 1.50 Mbps（QPSK）

CFO（載波頻率偏移）的物理本質是收發晶振頻率差，幀與幀之間幾乎不變（LEO 衛星最極端情況也僅約 1 subcarrier/幀漂移）。 因此每幀重掃 141 點是純冗餘計算，可以用「追蹤模式」大幅縮減計算量。

目標：Data Rate > 2 Mbps（QPSK）
結果：2.30 Mbps ✅
8PSK：2.95 Mbps ✅

§2 CFO 偵測原理（Pilot 能量最大化）

對每個候選偏移量 k，計算所有 pilot 子載波位置的接收能量總和：

E(k) = Σ_{p=0, p≠136}^{138} |Y[LEFT_GUARD + k + p×7]|² offset 正確 → 對準 pilot subcarrier → 能量大 offset 錯誤 → 落在 data subcarrier → 能量小

§3 追蹤狀態機設計

在 HLS 函式內宣告兩個 static 變數，在 FPGA 暫存器中跨幀保存：

static int cfo_state = 0; // 上一幀找到的最佳 offset static bool cfo_locked = false; // false = Unlocked, true = Locked
狀態行為掃描點數預估 cycles預估時間 @100MHz
Unlocked
（第一幀 / 重新鎖定）		 對全部 141 個 offset 計算 E(k)，argmax 得到 best_cfo，設 cfo_locked=true 141 42,864 428.6 µs
Locked
（第二幀起）		 僅掃 cfo_state ± 5（11 個候選點），argmax 得到新 best_cfo；若偏移超出邊界則解除鎖定 11 22 – 3,344 0.22 – 33.4 µs

Locked → Unlocked 觸發條件（boundary_hit）

drift = new_best_cfo - cfo_state if (drift >= CFO_TRACK_W || drift <= -CFO_TRACK_W) // CFO_TRACK_W = 5 cfo_locked = false; // 下一幀重新全掃

機制說明：若本幀在窄視窗（±5）內找到的最大能量點剛好落在視窗邊緣（drift = ±4 或 ±5）， 系統推斷真實 CFO 可能已漂移至視窗外，因此解除鎖定，下一幀執行全掃重新定位。

⚠ 注意： 此機制的前提是「若真實 CFO 超出視窗，argmax 傾向落在視窗邊緣」。 這是一個工程假設，尚未透過 csim 強制驗證。詳見 §5 擔憂①。

§5 設計假設與潛在問題

以下列出本設計成立所依賴的前提假設，以及尚待驗證的潛在風險。 標示 ⚠ 未驗證 的項目需要進一步 csim / 硬體實驗確認。

# 假設內容 依賴條件 狀態
A1 E(offset) 在正確 offset 附近呈現單峰（unimodal） 無多路徑嚴重干擾、SNR 足夠 ✅ 正常 SNR 下成立
A2 幀與幀之間 CFO 漂移不超過 ±5 subcarrier 載波頻率、LEO 速度、subcarrier spacing 三者決定 ⚠ 待計算驗證
A3 Loopback 環境下 CFO ≈ 0（收發共用晶振） 測試板架構確認 ✅ ZCU208 Loopback 確認
A4 argmax 在視窗外時傾向落在視窗邊緣（觸發 boundary_hit） 能量函數單峰性 + 邊緣候選點能量 > 中心點 ⚠ 工程假設，未以 csim 強制驗證
A5 所有 11 個視窗點能量皆低時，系統仍能正確響應 A4 成立才能靠 boundary_hit 救回 ⚠ 依賴 A4
擔憂 ①
argmax 落在視窗邊緣 — 未驗證
境界觸發（boundary_hit）的邏輯假設：若真實 CFO 已漂出 ±5 視窗， argmax 會落在視窗邊緣（drift = ±4 / ±5），從而觸發解除鎖定。 但若能量函數非常平坦，argmax 可能落在視窗中央，drift < 5，導致系統 不解鎖而繼續追錯誤的 offset。
⚠ 需要 csim 強制驗證：設 CFO_inject 超出 ±5，觀察 drift 分布
擔憂 ②
多路徑環境下可能出現多峰
多路徑傳播可能使 E(offset) 在多個 offset 位置出現峰值， 導致 argmax 在幀間抖動，觸發頻繁的 boundary_hit 並來回切換 Unlocked/Locked。 目前系統在 Loopback 環境下沒有此問題，但實際無線通道需重新評估。
⚠ Loopback 已驗證，無線通道未測試
擔憂 ③
無絕對能量門檻，無法偵測信號消失
目前系統只看相對能量（哪個 offset 能量最大），沒有絕對門檻。 若信號完全消失（如遮蔽），系統仍會在 11 個候選點中硬選一個 argmax， 繼續維持 Locked 狀態並輸出錯誤的 offset。
⚠ Loopback 無此問題，有遮蔽場景需加 min_energy 門檻
擔憂 ④
boundary_hit 當幀本身的解調品質
boundary_hit 發生的那一幀，系統已用「偏移的視窗」掃描， 得到的 offset 可能不正確，該幀的通道等化與解調品質有降低風險。 目前設計中 boundary_hit 幀仍會繼續解調（只是下一幀重掃）。
⚠ 低優先度；正常場景觸發率極低
擔憂 ⑤
±5 視窗寬度的物理依據尚未計算
CFO_TRACK_W = 5 的設定基於「LEO 每幀漂 ≤1 subcarrier」的粗略估計， 保留 5 倍裕量。但確切數值需要：載波頻率 × 最大徑向速度 / 光速 / subcarrier_spacing / 幀率 四個參數才能驗算。若實際漂移 > 5，系統會頻繁重新全掃，喪失追蹤效益。
⚠ 需確認載波頻率與 subcarrier spacing（詳見 §6）
擔憂 ⑥
CFO 突變（非漸進式漂移）
本設計假設 CFO 漂移是平滑漸進的。若發生突然的頻率跳變（例如 RF 前端 溫度突變、PLL 重鎖），單幀 drift 可能超過 5，觸發全掃。全掃耗時 428 µs， 在此期間若還有後續幀到達，pipeline 是否能正確處理需確認。
⚠ 低頻事件；Loopback 未測試

§6 ±5 視窗寬度的 Doppler 驗證（待完成）

驗證公式：

最大 Doppler shift = f_carrier × v_radial_max / c 每幀 Doppler 漂移 = Δ(Doppler shift) per frame 幀間漂移 subcarrier = 每幀 Doppler 漂移 / subcarrier_spacing 目標：幀間漂移 subcarrier ≤ 5 → CFO_TRACK_W = 5 安全
# 參數 取得方式 目前狀態
1 載波頻率 f_carrier（GHz） RF 前端規格書 / Vivado RF Data Converter IP 設定 待確認
2 LEO 最大徑向速度 v_max（m/s） 物理常數：LEO 軌道速度 ≈ 7,500 m/s，最差幾何 ≈ v_max ≈ 7,500 m/s（可用估算值）
3 OFDM Subcarrier Spacing（Hz） fs / FFT_size；查 Vivado BD 的 FFT IP 設定 待確認
4 Frame duration（µs） 硬體實測 QPSK 620 µs / 8PSK 717 µs ✅
取得參數 1 和 3 後可立即計算。若幀間漂移 > 5，需將 CFO_TRACK_W 調大並重新 synthesis。
